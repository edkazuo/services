Ambiente Local · Spark · MinIO · Hive Metastore · Delta Lake

Datalake local do zero — até virar Lakehouse de verdade

Spark para processar, MinIO como storage compatível com S3, Hive Metastore com MySQL como catálogo, Delta Lake trazendo transação ACID e versionamento — e uma interface em Streamlit por cima, pra não depender de notebook pra explorar o dado.

Por que não usar o padrão

Derby funciona — até a segunda sessão tentar conectar

O Hive já vem com um metastore embutido, sem precisar de nenhuma instalação extra. O problema não é ele funcionar mal — é ele ter uma limitação fundamental de design.

Apache Derby (padrão)

Banco embarcado que roda dentro do próprio processo JVM que o inicia. Ele trava o diretório metastore_db/ para uso exclusivo daquela JVM — a segunda sessão (outro notebook, outro spark-submit, outro usuário) simplesmente não consegue conectar.

MySQL (ou PostgreSQL)

Banco relacional real, rodando como serviço independente, aceitando múltiplas conexões JDBC simultâneas. Qualquer número de sessões Spark, de máquinas diferentes, pode consultar e escrever metadado ao mesmo tempo — sem lock de arquivo.

O erro que aparece na prática
ERROR XSDB6: Another instance of Derby may have already booted
the database /home/user/metastore_db.
Por que Delta Lake

O mundo analytics nunca teve "commit" e "rollback" — até agora

Banco transacional sempre teve essa garantia embutida: ou a transação inteira acontece, ou nada acontece, e dá pra desfazer. Parquet puro sobre um data lake nunca teve isso.

Parquet puro (sem Delta)

Escrita não é atômica entre múltiplos arquivos — um job que falha no meio pode deixar dado parcial. Não existe isolamento entre quem lê e quem escreve. E se um OVERWRITE ou UPDATE sair errado, não existe "desfazer" — só reprocessar tudo de novo a partir da fonte, se ainda existir.

Delta Lake

Mantém um log de transação (_delta_log) por trás do Parquet — cada escrita vira uma versão nova, atômica. Isso dá exatamente o que faltava: MERGE/UPDATE/DELETE com garantia ACID, e time travel — a capacidade real de voltar para qualquer versão anterior da tabela.

Passo a passo

Do zero ao primeiro SELECT

  1. 01Pré-requisitos e MySQL
    Java (JDK 11), e o banco que vai substituir o Derby.
    bash
    sudo apt update && sudo apt install -y openjdk-11-jdk mysql-server

# cria o schema e usuário dedicados ao metastore
sudo mysql -e "CREATE DATABASE metastore;"
sudo mysql -e "CREATE USER 'hive'@'localhost' IDENTIFIED BY 'hive123';"
sudo mysql -e "GRANT ALL PRIVILEGES ON metastore.* TO 'hive'@'localhost';"
sudo mysql -e "FLUSH PRIVILEGES;"
  2. 02Hive Metastore standalone
    Baixar o binário, configurar a conexão JDBC com MySQL, e inicializar o schema do catálogo.
    bash
    wget https://downloads.apache.org/hive/hive-4.0.0/apache-hive-metastore-4.0.0-bin.tar.gz
tar -xzf apache-hive-metastore-4.0.0-bin.tar.gz
export HIVE_HOME=~/apache-hive-metastore-4.0.0-bin

# driver JDBC do MySQL precisa estar no classpath do metastore
wget https://repo1.maven.org/maven2/com/mysql/mysql-connector-j/8.4.0/mysql-connector-j-8.4.0.jar \
  -O $HIVE_HOME/lib/mysql-connector-j.jar
    $HIVE_HOME/conf/metastore-site.xml
    <configuration>
  <property>
    <name>javax.jdo.option.ConnectionURL</name>
    <value>jdbc:mysql://localhost:3306/metastore?useSSL=false</value>
  </property>
  <property>
    <name>javax.jdo.option.ConnectionDriverName</name>
    <value>com.mysql.cj.jdbc.Driver</value>
  </property>
  <property>
    <name>javax.jdo.option.ConnectionUserName</name>
    <value>hive</value>
  </property>
  <property>
    <name>javax.jdo.option.ConnectionPassword</name>
    <value>hive123</value>
  </property>
</configuration>
    bash — inicializa o schema e sobe o serviço Thrift
    $HIVE_HOME/bin/schematool -dbType mysql -initSchema
$HIVE_HOME/bin/start-metastore # sobe o serviço na porta 9083
  3. 03MinIO como storage S3
    Sobe o servidor MinIO local e cria o bucket que vai servir de warehouse.
    bash
    wget https://dl.min.io/server/minio/release/linux-amd64/minio
chmod +x minio
./minio server ~/minio-data --console-address ":9001" &

# cliente mc para criar o bucket via linha de comando
wget https://dl.min.io/client/mc/release/linux-amd64/mc
chmod +x mc
./mc alias set local http://localhost:9000 minioadmin minioadmin
./mc mb local/warehouse
  4. 04Spark apontando para os dois
    Configurar Spark para falar Thrift com o Metastore e S3A com o MinIO — os jars de integração S3 precisam bater com a versão do Hadoop empacotada no Spark.
    spark-defaults.conf
    spark.sql.catalogImplementation          hive
spark.hive.metastore.uris                thrift://localhost:9083
spark.sql.warehouse.dir                  s3a://warehouse/

spark.hadoop.fs.s3a.impl                 org.apache.hadoop.fs.s3a.S3AFileSystem
spark.hadoop.fs.s3a.endpoint             http://localhost:9000
spark.hadoop.fs.s3a.access.key           minioadmin
spark.hadoop.fs.s3a.secret.key           minioadmin
spark.hadoop.fs.s3a.path.style.access    true
spark.hadoop.fs.s3a.connection.ssl.enabled false
  5. 05Validar com duas sessões ao mesmo tempo
    O teste que realmente prova que saiu do Derby: abrir duas sessões Spark simultâneas e confirmar que ambas enxergam o catálogo sem conflito.
    pyspark — sessão 1
    spark.sql("CREATE TABLE vendas (id INT, valor DOUBLE) USING parquet")
spark.sql("INSERT INTO vendas VALUES (1, 99.90)")
    pyspark — sessão 2, aberta em paralelo, outro terminal
    spark.sql("SELECT * FROM vendas").show()
# com Derby, a sessão 2 nem conseguiria abrir. Com MySQL, funciona.
  6. 06Adicionar Delta Lake ao Spark
    Duas configurações extras habilitam o formato Delta — depois disso, toda tabela criada com USING DELTA passa a ter transação ACID e versionamento automático.
    spark-defaults.conf — acrescentar
    spark.jars.packages                      io.delta:delta-spark_2.12:3.2.0
spark.sql.extensions                     io.delta.sql.DeltaSparkSessionExtension
spark.sql.catalog.spark_catalog          org.apache.spark.sql.delta.catalog.DeltaCatalog
    pyspark — recriando a tabela em Delta
    spark.sql("""
    CREATE TABLE vendas (id INT, valor DOUBLE)
    USING DELTA
    LOCATION 's3a://warehouse/vendas'
""")
  7. 07Provar o rollback de verdade
    O teste que mostra o ganho real: gerar um "erro de produção", e voltar no tempo sem precisar reprocessar nada.
    pyspark — o "oops"
    spark.sql("INSERT INTO vendas VALUES (1, 99.90), (2, 150.00)")

# alguém roda um UPDATE errado em produção
spark.sql("UPDATE vendas SET valor = 0")  # zerou tudo, por engano
    pyspark — o rollback
    # ver o histórico de versões da tabela
spark.sql("DESCRIBE HISTORY vendas").show()

# consultar como estava ANTES do erro, sem restaurar nada ainda
spark.sql("SELECT * FROM vendas VERSION AS OF 1").show()

# restaurar a tabela de verdade para aquela versão -- o "rollback"
spark.sql("RESTORE TABLE vendas TO VERSION AS OF 1")
  8. 08Interface em Streamlit
    Sem precisar subir uma sessão Spark inteira só pra visualizar — a biblioteca deltalake (bindings Rust) lê a tabela direto do MinIO, leve o suficiente para uma interface web simples.
    bash
    pip install streamlit deltalake pandas
    app.py
    import streamlit as st
import os
from deltalake import DeltaTable

os.environ["AWS_ACCESS_KEY_ID"] = "minioadmin"
os.environ["AWS_SECRET_ACCESS_KEY"] = "minioadmin"
os.environ["AWS_ENDPOINT_URL"] = "http://localhost:9000"
os.environ["AWS_ALLOW_HTTP"] = "true"

st.title("Vendas — Lakehouse local")

dt = DeltaTable("s3://warehouse/vendas")
versao = st.select_slider(
    "Versão (time travel)",
    options=list(range(dt.version() + 1)),
    value=dt.version(),
)

dt_versionada = DeltaTable("s3://warehouse/vendas", version=versao)
st.dataframe(dt_versionada.to_pandas())
st.caption(f"Exibindo versão {versao} de {dt.version()}")
    bash — subir a interface
    streamlit run app.py
  9. 09Consultar via DBeaver (ou qualquer cliente SQL)
    Streamlit é ótimo pra visualização fixa, mas analista de negócio geralmente quer SQL livre, num cliente que já conhece. Isso exige uma peça diferente do Hive Metastore Thrift (que só serve metadado): o Spark Thrift Server, que expõe o Spark inteiro via JDBC/ODBC.
    bash — subir o Spark Thrift Server
    # usa a mesma config do spark-defaults.conf já configurada
$SPARK_HOME/sbin/start-thriftserver.sh \
  --hiveconf hive.server2.thrift.port=10000 \
  --hiveconf hive.server2.thrift.bind.host=0.0.0.0
    DBeaver — configuração da conexão
    # Nova Conexão → Apache Hive (o driver do Hive fala com Spark Thrift Server)
Host:      localhost
Porta:     10000
Banco:     default
Usuário:   (deixe em branco ou "anonymous")

# DBeaver baixa o driver JDBC do Hive automaticamente na primeira conexão
    DBeaver — SQL editor, já enxergando o catálogo do MySQL
    SHOW TABLES;
SELECT * FROM vendas VERSION AS OF 1;
-- time travel funciona igual, direto do DBeaver, sem PySpark nenhum
    Diferença importante: Hive Metastore Thrift (porta 9083) só serve metadado — schema, localização de tabela. Spark Thrift Server (porta 10000) executa SQL de verdade — é ele quem o DBeaver precisa, não o metastore diretamente.
Nota: versões de pacote (Hive, conector MySQL, jars do Hadoop/S3A) mudam com frequência — confirme a versão exata compatível com a build do Spark que você está usando antes de reproduzir os comandos acima.
