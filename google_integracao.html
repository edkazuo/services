A integração que ninguém desenhou de propósito

Google Ads, Gmail, Drive e BigQuery não nasceram para funcionar juntos — cada um tem seu próprio modelo de identidade e permissão. Quando uma automação de negócio conecta os quatro, a documentação oficial raramente cobre o ponto exato onde eles se encontram.

As camadas

Três modelos de identidade que não se falam

Cada sistema resolve "quem pode acessar o quê" de um jeito próprio. A integração só funciona quando alguém entende as três ao mesmo tempo.

01 Google Ads — hierarquia MCC
Contas gerenciadoras (MCC) agrupam contas filhas (Customer ID), mas acesso concedido na MCC não propaga automaticamente para chamadas de API que apontam diretamente para a conta filha — é necessário o header login-customer-id, ou convite direto na conta filha.
02 Google Workspace — identidade humana vs técnica
Convites de acesso via e-mail (usuário humano) e credenciais de Service Account (identidade técnica) seguem fluxos de concessão completamente diferentes — e frequentemente são confundidos na hora de solicitar acesso, gerando pedido no canal errado.
03 GCP / Databricks — provisionamento vs atribuição de workspace
Um grupo criado no nível de conta (via sincronização automática com o provedor de identidade) não é automaticamente atribuído a nenhum workspace — isso exige uma etapa manual separada, frequentemente feita sem processo documentado.
Onde a documentação falha

O que raramente está escrito com clareza

✕
Erro de permissão sem causa óbvia
A API do Google Ads retorna permission_denied mesmo com acesso aparentemente concedido — a causa real (falta do header de MCC, ou acesso só na hierárquica) raramente aparece de forma direta na mensagem de erro.
✕
Convite de notificação ≠ acesso de dado
Google Ads permite convidar alguém apenas para "receber notificação por e-mail" da conta — visualmente parecido com convite de acesso real, mas sem nenhuma permissão de leitura de dado associada.
✕
Criação de identidade ≠ acesso a recurso
Em ambientes com integração via SCIM/IdP, a criação automática de um grupo não implica em acesso a nenhum workspace específico — essa é sempre uma segunda decisão, manual, tomada por quem administra a conta.
Boas práticas

O que reduz esse tipo de atrito

✓
Nomear a camada certa antes de pedir acesso
Separar explicitamente "acesso de usuário humano", "credencial de identidade técnica" e "atribuição de workspace" evita boa parte da confusão em pedidos de suporte.
✓
Credencial sempre em cofre gerenciado, nunca em arquivo solto
Qualquer JSON de Service Account ou token de API deveria nascer direto em um Secret Scope — nunca em repositório de código ou pasta pessoal, mesmo que "seja só um teste".
✓
Revisão periódica, não só concessão pontual
Conceder acesso corretamente uma vez não substitui revisão futura — pessoas mudam de time, projetos terminam, e acesso raramente é revogado de forma proativa sem um processo formal de recertificação.
Nota: este conteúdo descreve padrões gerais de arquitetura e problemas documentados publicamente pela própria Google, com base em experiência prática de integração. Não reproduz detalhes específicos de nenhum ambiente corporativo particular.
