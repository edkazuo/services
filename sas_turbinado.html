Join artesanal: hash como índice, POINT= como resposta

A maioria acha que SAS turbinado é %MACRO. Não é. É tratar hash object como índice de banco de dados, acesso a disco como ponteiro, e regra de negócio como dado que gera código — em vez de tentar resolver tudo numa query com vários JOINs.

join_artesanal.diff
- proc sort data=tabela_a; by chave; run; - proc sort data=tabela_b; by chave; run; - data saida; merge tabela_a tabela_b; by chave; run; - data saida_tratada; set saida; /* regra de negócio, 2ª passada */ run; + /* 1 passada: hash guarda só o ponteiro da tabela_b */ + dcl hash idx(dataset:"tabela_b", multidata:'y'); + idx.DefineKey('chave'); idx.DefineData('ptr'); idx.DefineDone(); + /* acesso direto por ponteiro, regra aplicada na mesma passada */ + set tabela_b point=ptr;
O problema

MERGE tradicional cobra o preço de duas ordenações e duas leituras

O caminho de curso/certificação é sempre o mesmo: PROC SORT nas duas tabelas, MERGE BY, e depois um segundo DATA STEP pra aplicar a regra de negócio em cima do resultado. Em ambiente de volume real — carteira de crédito, milhões de contratos — isso não é estilo, é custo de disco medido em minutos ou horas.

A alternativa "avançada" que a maioria conhece é hash object completo: carregar a tabela inteira em memória pra fazer lookup O(1). Funciona até a tabela ficar grande demais pra caber — e aí volta tudo pro sort/merge de novo.

A arquitetura

Hash não precisa guardar o dado. Só precisa guardar onde ele está.

A virada de chave: usar o hash como índice — guardando apenas a chave e um ponteiro (número da observação) — e usar POINT= pra materializar o registro completo só quando existe match de verdade.

Hash completo (comum)

Guarda todas as colunas da tabela satélite dentro do hash. Rápido, mas o consumo de memória escala com o tamanho da tabela inteira — inviável quando a tabela satélite também é grande.

Hash-de-ponteiro (turbinado)

Guarda só a chave + ptr (posição física do registro). O hash fica pequeno mesmo com tabela satélite enorme — e POINT= lê o registro completo só quando há match confirmado.

exemplo ilustrativo — nomes genéricos
/* Passada 1: constrói o índice — só chave + ponteiro */
ptr_b + 1;
if (situacao ne 'inativo') then rc = idx.add();

/* Passada 2: varre a tabela principal sequencialmente */
do until(eof);
   set tabela_a end=eof;
   rc = idx.find();
   do while (rc = 0);
      /* só aqui materializa o registro completo, por ponteiro */
      set tabela_b point=ptr rc=rc_b;
      /* regra de negócio aplicada na mesma passada, sem 2º data step */
      output;
      rc = idx.find_next();
   end;
end;

Isso é, na prática, um index nested loop join — a mesma estratégia que um otimizador de banco relacional escolhe quando existe índice numa das tabelas. A diferença é que aqui foi escrito à mão, num DATA STEP puro, sem SQL nenhum envolvido.

A segunda camada

Regra de negócio como dado, não como query complicada

Quando a regra de classificação depende de uma combinação grande de condições — carteira, segmento, tipo de pessoa, faixa de produto — a tentação é escrever um CASE WHEN gigante ou um SQL com vários JOINs condicionais. Isso empurra decisão complexa para dentro do otimizador, toda vez que o job roda.

Query com vários JOINs

O otimizador reavalia a lógica condicional a cada execução. Difícil de auditar — sem rodar EXPLAIN, ninguém sabe qual branch está sendo usado. Plano de execução muda conforme volume, silenciosamente.

Geração de código a partir de tabela

Uma tabela de regra vira, via hash + PUT, um programa IF/ELSE estático — gerado uma vez, incluído no job principal via %INCLUDE. A decisão já vem resolvida antes do dado real ser processado.

esqueleto ilustrativo do gerador
data _null_;
   file "regra_gerada.sas";
   /* itera a tabela de regra via hash + hiter, */
   /* escreve IF/ELSE já resolvido pra cada combinação */
   put 'if (segmento eq ' chave ') then pool = ' valor ';';
run;

/* no job principal, o código gerado é só incluído: */
%include "regra_gerada.sas";
A ideia central: trocar complexidade em runtime por complexidade em build-time. A lógica difícil é resolvida uma vez, na geração — e o processamento real, por maior que seja o volume, só executa comparações simples já achatadas.
Referência rápida

Peças do hash object que sustentam essa arquitetura

multidata: 'y'
Permite mais de um registro por chave — essencial quando um contrato tem várias garantias, por exemplo.
find_next()
Percorre todos os registros de uma mesma chave num hash multidata — o "cursor" que avança pela fila de ponteiros.
dcl hiter
Iterador de hash usado para varrer toda a tabela de regra durante a geração de código — sem precisar de PROC SQL / INTO :.
SET ... POINT=
Acesso direto a uma observação por posição física — o que transforma o ponteiro guardado no hash em dado real.
Dois cuidados que sustentam a mágica: desde a Versão 8 do SAS, POINT= funciona normalmente em dataset comprimido — a opção POINTOBS=YES já vem como padrão. A exceção real é quando o dataset foi criado com REUSE=YES (reaproveita espaço de observações deletadas) — nesse caso o SAS desliga o POINTOBS= automaticamente, e POINT= deixa de funcionar. O cuidado que continua valendo sempre: o ponteiro só é válido enquanto a ordem física da tabela satélite não mudar entre a carga do índice e a leitura. Vale documentar isso explicitamente no código — é o tipo de coisa que quebra silenciosamente meses depois.
