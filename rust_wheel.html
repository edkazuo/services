Quando encapsular em Python não basta

Um módulo Python esconde a lógica de quem usa a biblioteca — mas o código-fonte continua ali, legível, para quem tiver acesso ao repositório. Compilar essa lógica em Rust e distribuir como wheel tira o código-fonte de circulação: só o binário chega a quem consome.

Nota: todo código nesta página é ilustrativo e simplificado — propositalmente incompleto, não compila como está, e não reflete nenhuma implementação real. O objetivo é mostrar a estrutura do processo, não fornecer um exemplo pronto para reprodução.
Por que ir além do módulo Python

Dois níveis de encapsulamento, dois níveis de exposição

Módulo Python puro

Esconde a lógica de quem chama a função — mas o arquivo .py continua legível por qualquer pessoa com acesso ao código-fonte. Bom para organização, insuficiente quando a lógica interna (não só a credencial) precisa ficar fora de vista.

Extensão compilada (Rust + PyO3)

O que chega a quem instala via pip é um binário .so/.pyd — sem código-fonte legível junto. A lógica de descriptografia, validação e regra de negócio interna fica fora de alcance de quem só tem o pacote instalado.

Estrutura do processo

Do código Rust ao pacote instalável via pip

  1. 01Estrutura do projeto
    Um projeto Rust configurado como biblioteca dinâmica, com o crate PyO3 habilitado para gerar bindings Python.
    Cargo.toml — ilustrativo
    [package]
name = "minha_lib"
version = "0.1.0"
edition = "2021"

[lib]
name = "_native"
crate-type = ["cdylib"]

[dependencies]
pyo3 = { version = "0.22", features = ["extension-module"] }
# demais dependências (criptografia, parsing) entrariam aqui
  2. 02Esqueleto da lógica interna
    Estrutura simplificada mostrando o padrão: receber um segredo protegido, processar internamente, e expor só o resultado seguro — nunca o dado sensível bruto.
    src/lib.rs — esqueleto ilustrativo, não compilável
    use pyo3::prelude::*;

// segredo nunca em texto puro no código-fonte
const SEGREDO_PROTEGIDO: &str = "...";

// #[pyfunction] expõe esta função para o lado Python
#[pyfunction]
fn obter_info_segura(py: Python) -> PyResult<PyObject> {
    let dado_interno = processar_segredo(SEGREDO_PROTEGIDO)?;

    // expõe apenas campos não sensíveis do resultado
    let resultado = extrair_campos_seguros(py, &dado_interno)?;
    Ok(resultado)
}

// lógica interna -- nunca exportada, invisível para quem consome o pacote
fn processar_segredo(entrada: &str) -> PyResult<String> {
    // validação, descriptografia, chamada externa, etc.
    todo!()
}

// registro do módulo -- só o que está listado aqui fica acessível
#[pymodule]
fn _native(m: &Bound<PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(obter_info_segura, m)?)?;
    Ok(())
}
  3. 03Compilar como wheel
    maturin compila o Rust e empacota o binário resultante no formato wheel padrão do Python — o mesmo pipeline que usamos hoje mais cedo no GitHub Actions.
    bash
    pip install maturin
maturin build --release
# gera target/wheels/minha_lib-0.1.0-*.whl
  4. 04Wrapper Python fino
    O pacote instalado precisa de um __init__.py simples reexportando as funções do binário — é a única parte do pacote que continua sendo texto legível, e não contém lógica sensível nenhuma.
    minha_lib/__init__.py
    from ._native import obter_info_segura

__all__ = ["obter_info_segura"]
  5. 05Instalar e consumir
    Do lado de quem usa, a experiência é idêntica a qualquer biblioteca Python normal — sem nenhuma pista de que a lógica interna está compilada.
    bash + python
    pip install target/wheels/minha_lib-*.whl
    app.py
    import minha_lib
info = minha_lib.obter_info_segura()
# quem chama não tem como ver como "obter_info_segura" funciona por dentro
Isso não substitui boa prática de gestão de segredo (cofre gerenciado, rotação, princípio de menor privilégio) — é uma camada adicional, que dificulta engenharia reversa casual do código-fonte, não uma garantia absoluta de segurança.
